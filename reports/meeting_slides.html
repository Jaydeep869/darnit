Core Engine Fix • Issue #427

Plugin Handler Discovery Failure

darnit audit never called discover_implementations(), so no plugin handlers were registered.

Root Cause

High Severity
  • cmd_audit() in cli.py loads the framework config but skips discover_implementations()
  • All plugin handlers (repro_deps_pinned, repro_build_env_declared, etc.) never registered into SieveHandlerRegistry
WARNING: handler 'repro_deps_pinned' not found in registry
Result: Pass 0 | Fail 0 | Warn 5 (all fell back to manual)

Fix Applied

Tested

Added to cmd_audit() in cli.py:

from darnit.core.discovery import discover_implementations

# Discover plugin handlers before running audit
discover_implementations()
Verified on branch reproducibility-evaluation. Handlers now execute. Ready for PR.
Core Engine Fix • Issue #428

Non-Deterministic Control Ordering

set() iteration in merger.py:424 causes audit output order to vary between runs.

Root Cause

Idempotency
  • Running darnit audit --show-all twice on the same repo produces different output order
  • merger.py:424 uses set(framework.controls.keys()) which has random iteration order due to PYTHONHASHSEED
all_control_ids: set[str] = set(framework.controls.keys())
for control_id in all_control_ids:  # random order each run
    effective.controls[control_id] = ...

Connection to #418

Determinism Tier 1
  • Maintainer opened #418 for Tier 1 Determinism (sorting file walks, dicts, templates)
  • Our finding at merger.py:424 is a concrete instance of that umbrella
  • Fix: Sort control IDs or preserve framework order before populating effective.controls
With PYTHONHASHSEED=0, output was byte-identical. Fixing merger.py makes it deterministic by default.

Same seed, same code, different thread counts produce different SHA-256 hashes.

4. SHA-256

T=1: 5dd5...

T=2: 6cb0...

T=4: 049c...

Why Numbers Diverge

IEEE 754
  • Float non-associativity: (a+b)+c != a+(b+c)
  • OpenBLAS partitions matrix blocks across threads, accumulating partial sums in different order
  • Result: 763/2500 elements (30.52%) differ between 1 and 2 threads
  • Relative diff ~2.44e-7 (near machine epsilon), but SHA-256 hashes are completely different

Intra-Thread Consistency

Deterministic

3 consecutive runs with same thread count produce identical hashes:

T=1: 5dd51c55... (3 runs identical)
T=2: 6cb047cc... (3 runs identical)
T=4: 049c52bb... (3 runs identical)
Non-determinism is strictly from cross-thread scheduling, not code-level randomness.
Experiment 1 • Findings

Lockfile Blind Spot and Issue #429

Lockfiles pin packages but not BLAS thread scheduling. Plus a false positive on requirements.txt.

Lockfile Semantic Gap

Conceptual
  • uv.lock got a green PASS on RE-01.01 (DependenciesPinned)
  • But uv.lock pins the Python layer only, it is oblivious to BLAS/C thread scheduling
  • "Fully pinned" code still diverges 30.5% when thread count changes
Lockfiles ensure package integrity but cannot guarantee numerical reproducibility.

#429: False Positive on requirements.txt

Bug
  • requirements.txt with numpy==2.5.2 (exact pin) got a hard FAIL
  • repro_deps_pinned hardcodes requirements.txt as "loose manifest" without checking if versions are pinned
FAIL RE-01.01: Dependency manifests found but no lock files
Fix: Parse requirements.txt lines. If all have == or hashes, award PASS/WARN instead of FAIL.

Why Fast-Math Alters Results

SIMD
  • Under -O2/-O3, compiler preserves IEEE 754 order. Small floats added to large accumulator are lost to precision
  • -ffast-math enables -fassociative-math, vectorizes across SIMD lanes (addps), reorders tree to preserve small values
  • All three targets produced completely unique ELF binaries

What Darnit Reported

0/0/5 Warn
  • Zero visibility into compilation: did not detect C code compiled into shared library
  • repro_hermetic_build opened Makefile but only grepped for curl/wget
  • Completely ignored gcc invocations and -ffast-math flag
Darnit currently models repos as interpreted scripts, missing compiled extensions entirely.
Experiment 2 • Findings

Issues #432 and #433

Compiler flag detection and native toolchain awareness gaps.

#432: Compiler Flags Ignored

Blind Spot
  • repro_hermetic_build scanned Makefile and reported "No suspicious patterns found"
  • Neither gcc, clang, nor -ffast-math appeared in evidence or warnings
Fix: Add inspection for -ffast-math, -Ofast, -fassociative-math, -march=native

#433: Native Toolchains Overlooked

Heuristic Gap
  • repro_build_env_declared only checks for Docker, Nix, pyenv, nvm. Ignores Makefile toolchain defs (CC = gcc-13) and CMakePresets
  • repro_deps_pinned only checks Python/Cargo/npm lockfiles, ignoring Conan/vcpkg/system libs
Fix: When C/C++ files exist, check native build manifests and guide toward compiler pinning.
